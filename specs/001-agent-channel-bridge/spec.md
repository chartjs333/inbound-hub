# Feature Spec: Bidirectional Channel Gateway
# Shared protocol — Agent Channel Bridge v1
Status: proposed; no production activation.
Repositories: chartjs333/nginx-qa and chartjs333/inbound-hub, branches spec/agent-channel-bridge-v1.

## Contract
Keep existing inbound sprint proposal and explicit Play/Start untouched. This protocol operates ONLY on already-authorized active sprint agents.
Channel: channel_id, type human|device|service, capabilities, owner, project scope, availability, policy. Agents may use multiple channels.
Request envelope: schema_version=1, request_id, idempotency_key, correlation_id, project_id, sprint_id, assignment_id, agent_id, channel_id, operation, payload, created_at, deadline?, experiment_id?, checkpoint_id?.
Event envelope: schema_version=1, event_id, request_id, correlation_id, channel_id, event_type, occurred_at, received_at, content_ref?, sha256?, source_metadata.
Operations: send_message, request_data, request_observation, request_live_session. Event types: accepted, rejected, queued, delivered, human_unavailable, response_received, failed, expired, cancelled.
No arbitrary raw binaries inside messages; reference immutable artifacts.

## Rules
Manual Online/Offline state belongs to human, not agent. Offline -> never initiate voice/video call, but may queue/send asynchronous messages. Online -> call may be attempted; unanswered uses limited retries and async fallback. Unknown/stale presence treated as Offline.
QR identifies registered checkpoint context only; QR grants no access or device control. Cameras and voice are consent-based. Physical instrument actuation is OUT OF SCOPE for MVP, with explicit separate authorization and safety review before future support.
Authenticate transport in both directions, authorize project/agent/channel/action, protect against replay, cross-project access, malicious payloads, duplicate delivery and prompt injection. Ensure traceability for sample, instrument, operator and experiment.
Durable outbox/inbox, explicit delivery status and idempotent retry. Waiting for human must not block independent agents. 

## Stories
1. Hub receives authorized request from nginx-qa running agent and routes via type-specific adapter.
2. Human channel supports mobile availability toggle, asynchronous messages and conditional outgoing call.
3. Checkpoint QR resolves approved device/workstation metadata; voice/camera uploads observations to originating request.
4. Device or service can provide read-only data using dedicated adapters.
5. Hub returns correlated events to originating agent without generating another sprint proposal.
## Acceptance
Multi-channel addressing, capability negotiation, durable request lifecycle, human Offline no-call, device controls prohibited in v1, traceable data lineage.


## QR-driven discovery, mobile plugins and permission levels
- Scanning a registered QR discovers device identity and its signed plugin capability manifests; never treats QR or installation as authority. Registry describes manufacturer/model, adapter compatibility and supported data/interaction operations.
- Mobile app offers only compatible, approved, signed modules/features, with clear consent and platform-compliant installation. Server-side adapters remain distinct from phone modules. No download of arbitrary executable QR content.
- A plugin may be installed or active but locked. Every sensitive operation requires server-validated permission granting, based on human identity, agent identity, lab/project, device, specific plugin actions and session. Tiered access may differentiate view_metadata, read_data, capture_image, configure_device, and privileged control; last category excluded from MVP.
- A user can explicitly approve a scoped capability using step-up identity verification: an app-local PIN used to unlock a secure authenticator, or a one-time code generated by a trusted hardware/authenticator device; proof must be verified by trusted service with expiry, attempt limits, replay protection and audit. Never encode the PIN in QR, persist a plaintext PIN, or treat knowing a static PIN as sufficient by itself for high-risk operations.
- Revocation and expiry are immediate for subsequent calls; offline presence does not imply authorization. QR spoofing, plugin impersonation and cross-project escalation are rejected.


## Card-present-at-login and configurable assurance
- A researcher taps a registered cryptographic access card on a trusted reader ONCE to initiate the workstation session, and may remove it afterward. No requirement for continuous physical card presence.
- Policy defines `required_assurance_level` per device/plugin/action and records the actual `session_assurance_level`, authentication method/time, authenticated researcher and bound workstation. A simple static RFID UID is identification only and must not count as cryptographic proof.
- Session may perform allowed low-risk actions while valid. High-risk action prompts for fresh, action-bound step-up (PIN-backed smart card challenge, passkey, or approved separate factor) if required assurance/freshness is not met. Authentications never confer plugin/device rights by themselves.
- Idle timeout, absolute expiry, user logout, admin revoke, lost-card revocation and user switch terminate/lock session and associated scoped grants.
